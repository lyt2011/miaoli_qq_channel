# v0.2.0 - 2026-11-07

> 🧱 **单缓冲拆成「积压 + 渠道」双缓冲，中间插一层条件节点决定器。** 事件先全部落进积压缓冲，由提交器周期性询问决定器「这批要不要回」，通过后才搬进渠道缓冲交给 `miaoli_bot`。
>
> **本版只有框架，没有任何判断逻辑**：注册的条件节点数是 0，所以提交器目前一条消息都不会提交。

## Added

### 缓冲区

- `core/buffers/`：`BaseBuffer` 抽象基类（`get_length` / `get_data` / `consume` / `record`）与 `MessageBuffer` 实现（`deque(maxlen=size)`，头即最新）。
- `MessageBuffer.drain_into(other)`：把本缓冲区全部消息按「旧 → 新」搬进另一个缓冲区，搬完自清空。顺序翻转收进方法内部，调用方不必再操心两端 `appendleft` 的相互作用。

### 决定器

- `core/judge_decider/`：`JudgeDecider` 按 `priority` 降序逐个执行条件节点。
  - 任一节点返回 `MustReply` 立即返回，后续节点不再执行。
  - 全部节点只返回 `AddScore` / `None` 时，累加分数返回给调用方。
  - 单节点超出 `atimeout` 被 `asyncio.wait_for` 掐断；节点异常只记日志并跳过，不影响后续节点。
- `core/judge_decider/actions/`：`MustReply(reason)` 与 `AddScore(score, reason)`，`AddScore` 构造函数校验 `0 <= score <= 1`。
- `api/judge_ops.py`：`register_judge_node(func, priority)` 返回幂等注销函数，供主包与子插件注册条件节点，不必直接持有 `JudgeDecider`。

### 提交器

- `main.py`：`auto_submit()` 常驻异步任务，由 `on_startup` 里的 `create_deamon()` 用 `asyncio.create_task` 拉起；异常退出时 `_restart_deamon` 重启，取消时不再重启。

### 配置

- `SubmitConfig`（`interval` / `min_submit_score`）与 `JudgeConfig`（`timeout`），由 `PluginConfig` 汇总。

## Changed

- **单缓冲 → 双缓冲**：原来 `EVENT_BUFFER` 一个环形缓冲既收全部事件又直接被 `QQChannel` 取走；现在 `MESSAGE_BUFFER` 收全部事件，`CHANNEL_BUFFER` 只放决定器批准提交的那批。
- `EventBuffer` → `MessageBuffer`，文件从 `core/event_buffer.py` 移到 `core/buffers/message_buffer.py`。
- `pop(count)` → `consume(count)`：命名不指定从哪一端取，具体方向交给实现（`MessageBuffer` 从头即最新端取）。
- `QQChannel.drain()` 改用 `get_length()` / `consume()`，不再依赖 `__len__` 与 `pop`。
- `consts.py` → `consts/` 包（`store_keys.py`），键名跟着语义走：`EVENT_BUFFER` 拆成 `MESSAGE_BUFFER` / `CHANNEL_BUFFER`，新增 `RAW_CONFIG` / `JUDGE_DECIDER`。
- `record_anything` → `backlog_anything`：只写进积压缓冲，不再直接暴露给渠道。
- 配置从顶层 `buf_size: 30` 拆成 `channel.buf_size` / `message.buf_size` 两段，并新增 `submit` / `judge` 段。

## Removed

- `consts.py`（被 `consts/` 包取代）。
- `core/event_buffer.py`（被 `core/buffers/message_buffer.py` 取代）。

## Note

- **本版没有写任何判断逻辑**。`JudgeDecider` 里 0 个条件节点 → `decide()` 恒返回 `0.0`，小于默认 `min_submit_score: 1.0` → 提交器永不提交。要让消息流到渠道，得先注册至少一条能加分的条件节点。
- `min_submit_score` 的刻度是「一条规则被完全满足」：单节点返回值上限 `1.0`，所以 `1.0` = 至少一条拉满，`2.0` = 两条拉满。
- `AddScore` 的分数是**满足度**，不是重要性；重要性由 `MustReply` 或注册多次表达，不靠加大分数。
- 提交器与主包 `auto_wake` 各有一个 60 秒节拍，串起来最坏延迟约 120 秒。
- `config.example.yaml` 仍是旧的顶层 `buf_size` 结构，未同步。
